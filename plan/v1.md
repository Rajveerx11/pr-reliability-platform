# Version One Plan

Status: Approved direction, ready for foundation implementation  
Date: 2026-08-12  
Product: Approval-First GitHub App

## Outcome

Version one reviews a GitHub pull request with one AI agent. It verifies the result with
tests and Proof of Work. A human must approve every comment or code change before it is
sent to GitHub.

Version one is successful when it can:

1. Receive a signed pull request webhook.
2. Start one durable and idempotent review run.
3. Select useful repository context under a fixed token budget.
4. Return structured findings from one review agent.
5. Run tests and the Proof of Work gate in an isolated environment.
6. Show findings and evidence to a human reviewer.
7. Publish an approved comment exactly once.
8. Report defect recall, false-positive rate, latency, and known cost.

## Product flow

```text
GitHub pull request
        |
        v
Signed webhook -> Durable run -> Context -> One agent -> Tests + Proof gate
                                                          |
                                                          v
                                                Human approval inbox
                                                          |
                                                          v
                                               Approved GitHub comment
```

## Version-one scope

Included:

- GitHub App installation for one owner or organization.
- Pull request opened, reopened, and synchronized events.
- One review agent behind a provider-neutral interface.
- Changed-file and direct-dependency context selection.
- Durable retries, timeouts, cancellation, and idempotency.
- Sandboxed test execution.
- Proof of Work verification.
- Human approve or reject flow.
- Run, finding, approval, latency, usage, and cost records.
- Ten frozen golden pull request tasks before public comparison.

Deferred:

- Automatic code patches or commits.
- Test, security, and reviewer specialist agents.
- Agent debate on every pull request.
- RepoGraph or vector retrieval.
- Providers other than GitHub.
- Enterprise billing and policy builders.
- Multi-region deployment.

## Decisions

### DEC-001 — Build an approval-first GitHub App

Decision: Use Plan B. GitHub webhooks start review runs. Results wait in an approval inbox.

Why: This proves a real production workflow while keeping risky actions under human control.
It also creates a direct path to real users and measurable runs.

Affected paths:

- `apps/api/`
- `apps/web/`
- `workers/`
- `packages/contracts/`
- `docs/architecture.md`

### DEC-002 — Start with one agent

Decision: Version one uses one primary review agent. Specialist agents remain disabled.

Why: A single-agent baseline gives a fair control group. Multi-agent work is added only when
the same frozen evaluation set shows a useful quality gain.

Affected paths:

- `workers/src/pr_reliability_workers/`
- `evals/golden_prs/`
- `docs/evaluation.md`

### DEC-003 — Use Python and FastAPI for the control plane

Decision: Build the API and worker code in Python 3.12. Use FastAPI for webhook and product
API endpoints.

Why: Proof of Work is already Python. Shared language lowers integration cost and keeps the
first version focused.

Affected paths:

- `pyproject.toml`
- `apps/api/`
- `workers/`
- `packages/`

### DEC-004 — Use Temporal for durable workflows

Decision: Temporal owns run execution, retries, timeouts, cancellation, and human wait states.

Why: Pull request runs can last minutes and wait hours for approval. Workflow history is safer
than custom background-job state. It also prevents retry logic from spreading across services.

Affected paths:

- `workers/src/pr_reliability_workers/workflows/`
- `workers/src/pr_reliability_workers/activities/`
- `infra/compose/`
- `docs/architecture.md`

### DEC-005 — Use PostgreSQL with stable ownership fields

Decision: PostgreSQL stores product data. Public objects use ULIDs. Internal joins use bigint
IDs. Every owned row includes `owner_id` from the first migration.

Why: Stable public IDs avoid exposing database sequences. Early ownership fields prevent a
risky tenant migration later.

Affected paths:

- `migrations/`
- `apps/api/src/pr_reliability_api/`
- `packages/contracts/`
- `docs/architecture.md`

### DEC-006 — Use versioned JSON contracts

Decision: Webhook envelopes, run commands, findings, evidence, approvals, and publish commands
use strict versioned JSON shapes.

Why: Agents and services change at different times. Versioned contracts make invalid output
visible and keep replays possible.

Affected paths:

- `packages/contracts/src/pr_reliability_contracts/`
- `packages/contracts/tests/`
- `apps/api/`
- `workers/`

### DEC-007 — Keep Proof of Work behind an adapter

Decision: Install the published `proof-of-work-agent` package and call it through a small local
adapter. Application code does not import private Proof of Work modules directly.

Why: Proof of Work remains an independent product. One stable adapter limits coupling and
allows package upgrades without changing workflow code.

Affected paths:

- `packages/proof_adapter/`
- `workers/src/pr_reliability_workers/activities/`
- `docs/evaluation.md`

### DEC-008 — Run untrusted commands inside a real sandbox

Decision: Test execution runs in a disposable container with CPU, memory, time, filesystem,
process, and network limits. Verification fails closed when isolation is unavailable.

Why: Existing Proof of Work process containment is trusted-local protection, not a security
sandbox. Pull request code must not run directly on the host worker.

Affected paths:

- `workers/src/pr_reliability_workers/activities/`
- `infra/`
- `docs/security.md`
- `evals/golden_prs/`

### DEC-009 — Require human approval before every external write

Decision: Version one never posts comments, patches files, creates commits, or changes pull
request state without explicit approval.

Why: Agent findings can be wrong. Human approval limits damage and creates a clear audit event.

Affected paths:

- `apps/web/`
- `apps/api/`
- `workers/src/pr_reliability_workers/activities/`
- `packages/contracts/`
- `docs/security.md`

### DEC-010 — Use clear code, plan, and documentation boundaries

Decision: Plans live in `plan/`. Documentation lives in `docs/`. Runtime code lives under its
owning application, worker, or package. Files stay focused and medium-sized.

Why: Clear ownership makes the project easier to navigate, test, review, and maintain.

Affected paths:

- `plan/`
- `docs/`
- `apps/`
- `workers/`
- `packages/`
- `AGENTS.md`

### DEC-011 — Track every feature with a GitHub issue

Decision: Create one GitHub issue before each feature. Every pull request links its issue and
relevant decision. Large features use smaller child issues.

Why: Issues give work a visible scope, acceptance criteria, dependency order, and history.

Affected paths:

- `.github/ISSUE_TEMPLATE/`
- `AGENTS.md`
- `Changes.md`

### DEC-012 — Start with OpenAI behind a provider-neutral interface

Decision: The first hosted baseline uses the OpenAI API through a narrow `ModelClient`
interface. Local CLIs remain available for evaluation fixtures.

Why: One provider keeps the first slice small. The interface prevents provider details from
entering workflow, data, and approval code.

Affected paths:

- `workers/src/pr_reliability_workers/agents/`
- `packages/contracts/`
- `.env.example`
- `docs/development.md`

### DEC-013 — Deploy to one cloud VM after local validation

Decision: Develop with local containers. Deploy the first private version to one cloud VM
after the end-to-end local flow passes.

Why: One VM is enough for first users, costs less, and still proves deployment, monitoring,
backup, and recovery. More complex infrastructure waits for measured load.

Affected paths:

- `infra/compose/`
- `infra/deployment/`
- `docs/development.md`
- `docs/security.md`

## Planned data model

Core tables:

- `repositories`: GitHub installation and repository identity.
- `pull_requests`: pull request number, base SHA, and head SHA.
- `runs`: workflow identity, status, attempt, budget, timing, and cost.
- `findings`: typed claim, severity, file location, evidence, and confidence.
- `approvals`: actor, decision, target finding, and decision time.
- `run_events`: ordered, append-only audit events with safe payloads.

Rules:

- Unique run key: repository, pull request number, and head SHA.
- Unique external action key: run, action type, and target SHA.
- Findings always point to the analyzed head SHA.
- Missing usage remains unknown. It is never stored as zero.

## Delivery phases

### Phase 0 — Repository foundation

- Create folder structure and repository rules.
- Freeze version-one decisions.
- Add documentation and issue templates.
- Create feature issues in dependency order.

Exit check: repository is private, clean, pushed, and all planned features have issues.

### Phase 1 — Local single-agent baseline

- Add versioned contracts.
- Create one golden pull request fixture.
- Select changed files and direct imports under a fixed budget.
- Run one agent and validate structured findings.

Exit check: seeded defect is found with valid evidence and recorded run facts.

### Phase 2 — Durable GitHub workflow

- Verify GitHub webhook signatures.
- Store repository and pull request records.
- Start, retry, cancel, and replace Temporal workflows safely.

Exit check: webhook replay creates no duplicate run. New commits supersede old runs.

### Phase 3 — Verification and approval

- Execute tests in a disposable sandbox.
- Run the Proof of Work adapter.
- Build approval inbox.
- Publish approved comments idempotently.

Exit check: failed verification blocks output. Retried publishing creates one comment.

### Phase 4 — Evaluation and first deployment

- Expand to ten frozen golden pull request tasks.
- Record recall, false positives, latency, retries, usage coverage, and cost.
- Add traces, health checks, backup, restore, and runbook.
- Deploy private version to one VM.

Exit check: full flow passes locally and in deployment with a public methodology report.

### Phase 5 — Multi-agent experiment

- Expand frozen set toward 30 to 50 tasks.
- Add specialist routing behind feature flags.
- Compare one agent and specialists on the same tasks and limits.

Exit check: specialists ship only when measured quality gain beats agreed cost and latency caps.

## Verification rules

Every feature must include:

1. Unit tests for local logic.
2. Contract tests for every message boundary.
3. Integration tests for PostgreSQL, Temporal, GitHub, or the sandbox when touched.
4. One end-to-end test when user flow changes.
5. A `Changes.md` entry linked to the feature issue and decision.
6. No secrets, raw prompts, source files, or agent output in persistent logs.

## Version-one completion

Version one is complete when:

- Ten golden tasks run from a frozen version.
- Defect recall and false-positive rate are published.
- Success rate, p50/p95 latency, and exact known cost are published.
- Unknown usage is clearly shown.
- Every external write requires approval.
- GitHub retries cannot duplicate runs or comments.
- Threat model, architecture, runbook, demo, and limitations are documented.
